# GGS Books-of-Life Experiments

Experiments using the synthetic **Denmark GGS-II Harmonized Histories** "books of
life" data, generated by the separate
[`ggs-hh-dk-synthetic`](https://github.com/niznik-dev/ggs-hh-dk-synthetic) repo.
Each respondent is rendered as a key:value record; binary targets are derived
from a held-out outcome column that is dropped from the input to prevent leakage.

> **Synthetic only.** This data is modeled on the public GGS-II codebook, not real
> respondent microdata. See the generator repo's `CLAUDE.md` for the no-real-data
> constraint.

## Available Tasks

| Task | Question | Derived from | Classes |
|------|----------|--------------|---------|
| **ever_kid** | Has this respondent ever had a child? | `KID_1` (`KID_*` dropped from input) | 0 = no / 1 = yes |

## Dataset

- **Format**: `{"train": [...], "validation": [...], "test": [...]}`, each entry `{input, output}` — the standard cruijff_kit shape.
- **Input**: ~39 demographic / family-background fields as `KEY: value | ...`, ending at `PARDIVEV`.
- **Target**: `output` is `"1"` / `"0"`.
- **Example file**: `ggs_hh_dk_basic_books_of_life.json` (40,000 train / 5,000 validation / 5,000 test; ~63% positive).

## Binary Evaluation Task

**Script:** `blueprints/ggs/inspect_task.py`

**Available aliases:**
- `@ever_kid` — ever-had-a-child prediction
- `@ggs_binary` — generic, for any future GGS books-of-life binary target

### Usage

Evaluate a fine-tuned model:
```bash
inspect eval blueprints/ggs/inspect_task.py@ever_kid \
    --model hf/model_name \
    -M model_path=/path/to/checkpoint/epoch_0 \
    -T data_path=/path/to/ggs_hh_dk_basic_books_of_life.json \
    -T config_path=/path/to/eval.yaml
```

Evaluate a base model (no fine-tuning):
```bash
inspect eval blueprints/ggs/inspect_task.py@ever_kid \
    --model hf/Llama-3.2-1B-Instruct \
    -M model_path=/path/to/pretrained/Llama-3.2-1B-Instruct \
    -T data_path=/path/to/ggs_hh_dk_basic_books_of_life.json \
    -T config_path=/path/to/eval.yaml
```

**Note:** `config_path` is the run's `eval.yaml` (scaffolded for you), which provides
`system_prompt` and `prompt`. For a standalone base-model eval, hand-write a simple
`eval.yaml` with just those fields.

### Task Parameters

| Parameter | Default | Description |
|-----------|---------|-------------|
| `data_path` | required | Path to JSON dataset |
| `config_path` | `""` | Path to eval.yaml (reads prompt/system_prompt) |
| `split` | `test` | Data split: train, validation, or test |
| `temperature` | `1e-7` | Generation temperature |
| `max_tokens` | `5` | Max tokens to generate |
| `use_chat_template` | `True` | Wrap prompt with the model's chat template. Set `False` for base (non-instruct) models. |
| `assistant_prefix` | `""` | If set, prefill an assistant turn with this string. See "Evaluating base models" below. |
| `top_logprobs` | `20` | Number of top tokens to return logprobs for. |

### Evaluating base (non-instruct) models

Base models often won't emit a clean `"1"` / `"0"` when handed a chat-template prompt —
they continue the document instead of answering. Two knobs help:

- `use_chat_template=False` skips the chat wrapper so the prompt is fed as raw text.
- `assistant_prefix="Answer: "` (or whatever leads naturally into the label in your
  prompt) prefills an assistant turn, so the next token lands in the answer position.

### Scoring

`risk_scorer` (logprob-based P(1) over `["0", "1"]` for calibration and AUC) and
exact `match` on the binary output. Enable both in the run's eval config:

```yaml
scorers:
  - name: risk_scorer
    params:
      option_tokens: ["0", "1"]
  - name: match
    params:
      location: exact
      ignore_case: false
```

## Research Questions

1. **Does fine-tuning beat base?** How much does fine-tuning lift accuracy / AUC over a base model, given the ~63/37 class skew?
2. **Model size vs. signal:** Do larger models extract more predictive signal from the demographic features?
3. **Calibration:** Does fine-tuning improve or harm calibration on this skewed target?
